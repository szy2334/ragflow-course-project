多智能体论文问答与评审系统

需求文档（精简版）

版本：V2.0  |  架构：双知识库 + 四智能体 + RAGFlow + LangGraph

| 方案结论：方案清晰且可实现。系统以自由问答为唯一入口，由主控智能体自主判断是否仅检索用户论文库，或同时检索公共评审知识库；两名评审智能体对抗式输出观点，最终答案必须附带论文原文摘要或证据片段。 |
| --- |

# 1. 项目目标

构建一个面向科研论文的智能问答与评审系统。用户上传论文后，可围绕论文内容自由提问；系统既能完成事实问答，也能在需要时调用公共评审标准，对论文进行评分、评价和问题分析，并给出带原文证据的回答。

# 2. 用户可用功能

| 功能 | 用户操作 | 系统输出 |
| --- | --- | --- |
| 论文上传 | 上传 PDF 等论文文件 | 解析状态、论文信息、可问答状态 |
| 自由问答 | 输入任意与论文有关的问题 | 回答、论文原文摘要/证据、来源位置 |
| 论文评价 | 直接提问“实验是否充分”“方法有什么问题”等 | 评价结论、评分或等级、正反观点、证据 |
| 连续追问 | 围绕前一回答继续提问 | 结合对话上下文和论文证据继续回答 |

说明：系统不提供“一键生成完整评价报告”按钮，所有分析均由用户问题触发。

# 3. 知识库设计

| 知识库 | 存储内容 | 主要用途 |
| --- | --- | --- |
| 用户论文库 | 用户上传并清洗后的论文全文；每篇论文保留独立文档 ID、用户 ID 和任务 ID | 事实问答、章节定位、方法/实验/结论提取、原文证据引用 |
| 公共评审知识库 | 清洗后的论文评分标准、实验设计规范、写作规范、常见问题及评价准则 | 为评分、评价和问题诊断提供外部依据 |

检索原则：默认先检索当前用户论文；仅当问题涉及“是否合理、是否充分、如何评价、能否评分”等规范性判断时，才追加检索公共评审知识库。

# 4. 智能体设计

| 智能体 | 职责 | 主要输入与输出 |
| --- | --- | --- |
| 主控智能体 | 识别问题意图、选择知识库、调度其他智能体、汇总答案 | 输入：用户问题与会话状态；输出：执行路线与最终回答 |
| 论文理解智能体 | 检索并忠实提取论文中的事实、结构和证据 | 输出：论文事实、原文摘要、章节/片段引用 |
| 评审智能体 A | 偏严格审稿视角，主动寻找方法、实验和论证中的不足 | 输出：问题、扣分理由、证据 |
| 评审智能体 B | 偏辩护与平衡视角，验证评价是否过度并补充优点 | 输出：反驳、补充观点、证据 |

两名评审智能体采用对抗式运行：A 提出批评，B 进行核验、反驳或补充，主控智能体综合双方证据后给出平衡结论。

# 5. 核心业务流程

1. 用户上传论文，系统通过 MinerU/OCR 完成解析与清洗，并上传至 RAGFlow 用户论文库。

1. RAGFlow 对论文切块、向量化并建立索引，后台保存 paper_id、dataset_id 和 document_id 的映射关系。

1. 用户提交问题，主控智能体判断问题属于事实问答还是评价类问题。

1. 事实问答：调用论文理解智能体，仅检索当前论文，生成答案并附原文证据。

1. 评价类问题：先由理解智能体提取论文事实，再检索公共评审知识库；两名评审智能体对抗式分析。

1. 主控智能体检查证据、处理冲突并生成最终回答。

# 6. 问题路由规则

| 用户问题示例 | 检索范围 | 调用智能体 |
| --- | --- | --- |
| “论文用了什么数据集？” | 仅当前论文 | 主控 + 理解 |
| “作者为什么选择该指标？” | 优先当前论文；证据不足时可补充公共库 | 主控 + 理解 |
| “实验设计是否充分？” | 当前论文 + 公共评审知识库 | 主控 + 理解 + 评审 A/B |
| “请给这篇论文的实验部分评分。” | 当前论文 + 评分标准 | 主控 + 理解 + 评审 A/B |
| “这篇论文有哪些问题？” | 当前论文 + 公共评审知识库 | 主控 + 理解 + 评审 A/B |

# 7. 输出要求

- 回答正文：直接回应用户问题，避免泛泛而谈。

- 证据摘要：至少提供一段来自当前论文的原文摘要或检索片段；评价类问题还应标明使用的评审标准。

- 来源信息：返回论文文档名、章节/页码（可获得时）、文本块 ID 或引用序号。

- 不确定性说明：当论文证据不足或两名评审分歧较大时，必须明确说明。

- 评分约束：评分必须绑定具体维度和评分标准，禁止只输出无依据的总分。

# 8. 系统架构与组件

| 组件 | 作用 |
| --- | --- |
| 前端 | 论文上传、问答交互、证据展示、解析进度展示 |
| 后端 API | 用户、论文、会话、问题与结果管理 |
| LangGraph | 状态管理、问题路由、智能体编排、对抗评审与结果汇总 |
| RAGFlow | 双知识库管理、文档解析后索引、混合检索、原文片段返回 |
| 大模型服务 | 意图判断、论文理解、评审推理和自然语言生成 |
| 业务数据库 | 保存用户、论文映射、会话、消息、执行记录和引用信息 |

# 9. 关键数据字段

| 对象 | 关键字段 |
| --- | --- |
| 论文 | paper_id、user_id、file_name、dataset_id、document_id、parse_status |
| 会话 | session_id、user_id、paper_id、created_at |
| 消息 | message_id、session_id、question、answer、route_type |
| 引用 | document_id、chunk_id、source_text、section、page、similarity |
| 评审结果 | dimension、score、review_a、review_b、final_judgement、evidence |

# 10. 非功能要求

- 权限隔离：检索用户论文时必须限定 user_id 和当前 document_id，防止跨用户数据泄露。

- 可追溯性：每个事实判断和评价结论均应能回溯到论文证据或评审标准。

- 可复现性：模型、提示词、检索参数和评分标准需版本化记录。

- 可维护性：智能体、RAGFlow 服务、模型调用和前端接口分层开发。

- 安全性：所有 API Key 使用环境变量保存，不上传 GitHub。

# 11. 验收标准

- 用户能够上传论文，并在解析完成后进行自由问答。

- 事实问题只检索当前论文，回答包含正确且可查看的原文证据。

- 评价类问题能够自动追加检索公共评审知识库，无需用户手动选择。

- 两名评审智能体能输出不同视角，主控能处理冲突并生成平衡结论。

- 评分结果包含评分维度、标准、理由和论文证据。

- 系统不会将其他用户论文或测试集标准答案混入当前回答。

# 12. 实施建议

本方案可以直接进入开发。第一版建议先实现“上传论文 → 当前论文问答 → 证据展示”，再加入公共知识库路由，最后接入双评审对抗机制。对抗评审应设置最大轮次（建议 1 轮交叉核验），避免成本和响应时间失控。
